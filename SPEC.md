# Diorama Rail — Implementation Spec (v0.1, first cut)

You are implementing the first working version of **Diorama Rail**. It is a browser application that shows a model-railway layout in a low-poly, diorama-like style: trains running through terrain, stations, towns and forests. It is purely for watching, so there are no game mechanics.

Read this entire document before writing code. Where this spec is explicit, follow it. Where it is silent, choose the simplest option that keeps the code short and readable. Do not add dependencies beyond those listed.

---

## 1. Goals and non-goals

### Goals
1. **Pleasant to watch.** Use flat-shaded low-poly geometry, a coherent palette and gentle camera motion, with many small things moving at once ("Wimmelbild").
2. **Runs on weak hardware.** It must reach 60 fps on an integrated GPU (Intel UHD 620 class) at 1080p with `devicePixelRatio` capped at 1.5. It uses WebGL2 only.
3. **Data-driven.** A layout is a single JSON document. Everything visible (geometry, scenery, traffic) is derived deterministically from that JSON plus a seed.
4. **Machine-operable.** Layouts can be validated, simulated and screenshotted headlessly from a CLI. Errors are precise and machine-readable, so an AI pipeline can generate and repair layouts in a loop.
5. **Small and readable.** The target is roughly 3,000–4,000 lines of TypeScript in total. The owner will modify the code by hand, so favour clarity over cleverness.

### Non-goals (do NOT build in v0.1)
- A GUI layout editor. Editing happens in JSON, with hot reload.
- Realistic signalling, timetables, passengers, economy or sound.
- Easement curves (clothoids), superelevation, or a physics engine.
- WebGPU, textures, an ECS framework, React or any other UI framework.
- Mobile touch controls. Leave them out, but don't break touch orbiting if OrbitControls already provides it.

## 3. Architecture

Data flows one way. `model/` and `sim/` are **pure TypeScript with no DOM and no three.js imports**, so they run in Node.

```
layout.json ──► model/   parse + validate + build geometry (track graph, heights, terrain, scenery placements)
                   │
                   ├──► sim/     fixed-timestep simulation of trains (and later ambient agents)
                   │
                   └──► scene/   three.js: builds meshes once from the model, reads sim state each frame
cli/  ── check | simulate | schema | screenshot     (thin wrappers over model/ and sim/)
```

### Coordinate conventions (important)
- The model uses metres at **full scale**: **x = east, y = north, z = up**.
- three.js is y-up. Map model `(x, y, z)` to three `(x, z, -y)` in **one** helper, `toThree()`, in `scene/`. Never mix the two frames.
- Headings are radians, counter-clockwise from +x.
- Track positions are expressed as `(trackId, s)`, where `s` is the arc length in metres from the track's start.

## 4. Layout schema (`model/schema.ts`)

Define this with Zod and export the inferred TS types. Apply every default in the schema itself, so the rest of the code sees fully-populated objects. Unknown keys are an error (`.strict()`), which catches LLM typos.

```ts
type Vec2 = [number, number];

type Layout = {
  version: 1;
  name: string;
  seed: number;                       // default 1
  terrain: {
    size: Vec2;                       // [width, height] metres; origin at (0,0) bottom-left
    cell: number;                     // heightmap cell size, metres. default 4
    baseHeight: number;               // default 0
    seaLevel: number | null;          // default null (no water). Water plane drawn at this z
    features: Array<{                 // gaussian bumps; negative height = valley/basin
      at: Vec2; radius: number; height: number;
    }>;                               // default []
    noise: { amplitude: number; scale: number };   // default {amplitude: 2, scale: 120}
  };
  tracks: Track[];                    // min 1
  stations: Station[];                // default []
  services: Service[];                // default []
  scenery: {
    towns: Array<{ near: string | Vec2; radius: number; density: number }>;   // near = station id or point; density 0..1
    forests: Array<{ at: Vec2; radius: number; density: number }>;
    scatterTrees: number;             // 0..1, sparse trees everywhere else. default 0.15
  };
  style: {
    season: "summer" | "autumn" | "winter";   // default "summer"
    timeOfDay: number;                        // 0..24, default 15
    dayLengthSeconds: number | null;          // null = time frozen. default null
  };
};

type Waypoint = Vec2 | { at: Vec2; z?: number; radius?: number };   // radius overrides track.minRadius at this corner

type TrackEnd = {
  track: string;                      // parent track id
  at: number;                         // s on parent, metres
  heading: "forward" | "backward";    // which way along parent the branch leaves/arrives. default "forward"
};

type Track = {
  id: string;                         // /^[a-z][a-z0-9-]*$/
  kind: "loop" | "line";
  points: Waypoint[];                 // loop: >= 3; line: >= 1 if from/to given, else >= 2
  minRadius: number;                  // default 40
  maxGrade: number;                   // default 0.035
  from?: TrackEnd;                    // line only: starts at a junction on another track
  to?: TrackEnd;                      // line only: ends at a junction on another track
};

type Station = {
  id: string;
  name: string;
  track: string;
  at: number;                         // s of platform centre
  length: number;                     // platform length, default 120
  side: "left" | "right" | "both";    // relative to track direction; default "right"
};

type Service = {
  id: string;
  train: keyof typeof TRAIN_CATALOG;  // e.g. "regional-3", "express-6", "freight-10", "tram-2"
  color?: string;                     // hex; default from catalog
  route: string[];                    // ordered track ids; consecutive ids must share a junction
  mode: "loop" | "shuttle";           // loop: route must be closed; shuttle: reverse at ends
  stops: string[];                    // station ids to stop at (must lie on route). default []
  dwell: number;                      // seconds at each stop, default 25
  count: number;                      // number of trains on this service, default 1
};
```

### Train catalog (`model/catalog.ts`)
Each entry: `{ cars: number, carLength: number, carWidth: 3, carHeight: number, maxSpeed: m/s, accel: m/s², decel: m/s², color: hex, shape: "multiple-unit" | "loco-hauled" | "tram" | "freight" }`. Provide at least these four:

| id | cars | carLength | maxSpeed | accel | decel |
|---|---|---|---|---|---|
| `regional-3` | 3 | 22 | 30 | 0.8 | 1.0 |
| `express-6` | 6 | 25 | 45 | 0.6 | 0.9 |
| `freight-10` | 1 loco + 10 wagons | 18 / 14 | 22 | 0.3 | 0.6 |
| `tram-2` | 2 | 14 | 15 | 1.0 | 1.2 |

These speeds are deliberately calm, because this is a diorama. Also provide a global `TIME_SCALE` (default 1). The camera and HUD can expose 1×, 2× and 4× speed.

## 5. Model: geometry and graph

### 5.1 Segments (`geometry.ts`)
A track is a list of segments. Each segment is either:
- `{type:"line", p0, p1}`, or
- `{type:"arc", center, radius, startAngle, sweep}`, where `sweep` is signed (positive = counter-clockwise).

Each segment provides `length`, `pointAt(u)`, `headingAt(u)` and `curvature`. A track provides `pointAt(s)`, `headingAt(s)` and `segmentAt(s)` using a cumulative-length table and binary search.

### 5.2 Fillet construction (the core algorithm)
Turn a polyline of waypoints into tangent-continuous straight and arc segments:
1. For each interior corner `P_i` with incoming direction `d1` and outgoing direction `d2`:
   - Compute the turn angle `θ = angle(d1, d2)` and the radius `r` (the waypoint's own radius, else `minRadius`).
   - The tangent length is `t = r · tan(θ/2)`.
   - The arc runs from `P_i − d1·t` to `P_i + d2·t`.
2. For a `loop`, every vertex is a corner, including the wrap-around. Define `s = 0` at the start of the straight leaving waypoint 0 toward waypoint 1, i.e. just after the fillet at waypoint 0.
3. For a `line`, the first and last waypoints are endpoints, not corners.
4. **Fit check:** on every straight between corners `i` and `i+1`, the two tangent lengths must satisfy `t_i + t_{i+1} ≤ |P_{i+1} − P_i|`. Otherwise report `FILLET_OVERLAP`, giving both waypoint indices and the shortfall in metres.
5. If θ < 0.5°, skip the corner and merge the straights. If θ > 170°, report `CORNER_TOO_SHARP`.

### 5.3 Junction departure and arrival (`from` / `to`)
For `from: {track: P, at: s, heading}`:
1. Let `J = P.pointAt(s)` and `h = P.headingAt(s)`, plus π if `heading` is `"backward"`.
2. The branch's first segment is an arc of radius `minRadius`, tangent to `h` at `J`. It curves toward the side (left or right) where the first waypoint `W` lies.
3. The arc continues until its tangent line passes through `W`. Compute this with the standard tangent-from-external-point-to-circle construction, choosing the tangent that matches the arc's turning direction.
4. From there, the rest of the line is the fillet construction from §5.2, using the arc's end point as the polyline's first point.
5. If `W` lies inside the turning circle, report `JUNCTION_UNREACHABLE`.

For `to: {...}`, build the same construction from the parent's point outward with the heading reversed, then reverse the resulting segments and append them.

A track's position at a junction is shared exactly. Its z at that point is taken from the parent (see §5.5).

### 5.4 Track graph (`trackGraph.ts`)
- **Nodes:** track endpoints (buffer stops), plus junction points on parent tracks.
- **Edges:** maximal sub-ranges of a track between nodes, stored as `(trackId, s0, s1)`.
- **Switches:** every junction is a switch, with `{id, node, parentTrack, parentS, branchTrack, branchEnd: "start"|"end", heading, state: "straight"|"diverging"}`.
- Provide `next(trackId, s, direction, switchStates)` → the edge and direction a train enters when it reaches the end of its current edge, or `null` at a buffer stop.
- Process tracks in dependency order: parents before children. A cycle in `from`/`to` references is reported as `TRACK_REF_CYCLE`.

### 5.5 Heights (`heights.ts`)
Steps, applied per track in dependency order:
1. Sample the track every 5 m.
2. **Base profile.**
   - If any waypoints carry `z`, interpolate z linearly by `s` between those waypoints, and hold the end values constant beyond the first and last.
   - Otherwise sample the **unmodified** terrain at each point and smooth it with a moving average over a 120 m window.
3. **Pin junctions.** At junction ends, pin z to the parent's z at that `s`.
4. **Clamp grade.** Do a forward pass and then a backward pass, limiting `|dz/ds|` to `maxGrade`. Pinned points and explicit waypoint z values are hard constraints. If a constraint cannot be met, report `GRADE_EXCEEDED` with the s-range and the required grade.
5. **Classify structure** along `s` using `g = trackZ − groundZ`:
   - `bridge` where `g > 5`;
   - `tunnel` where `g < −7`;
   - `ground` otherwise.

   Merge runs shorter than 20 m into their neighbours, so structures don't flicker on and off. Store this as a list of `{kind, s0, s1}` spans.

### 5.6 Terrain (`terrain.ts`)
1. Build a heightmap grid of `size / cell` cells:
   `z = baseHeight + Σ gaussian(feature) + noise.amplitude · fbm(x/scale, y/scale, seed)`.
2. **Corridor shaping**, only on `ground` spans: for each grid vertex within `4 m + 1.5·|Δz|` of the nearest track sample, blend the vertex z toward `trackZ − 0.4`. The weight is 1 inside 4 m, then falls off linearly. This produces embankments and cuttings at roughly a 1:1.5 slope. Use a spatial hash of track samples so the cost stays reasonable.
3. Never shape terrain inside `tunnel` spans. The terrain mesh naturally hides tunnelled track.
4. Provide `groundZ(x, y)` using bilinear interpolation, for both the original and the shaped map.

### 5.7 Scenery placement (`scenery.ts`)
All placement is deterministic from `seed`. Each placement is a plain record `{kind, variant, x, y, z, rotation, scale, color}`.

- **Exclusion mask.** Nothing may be placed:
  - within 8 m of any track;
  - on a platform;
  - in water (`z < seaLevel + 0.5`);
  - on slopes steeper than 35° (trees) or 15° (houses).
- **Towns.**
  - Use Poisson-disc sampling inside the radius, at a spacing of `lerp(30, 12, density)`.
  - Houses face the nearest track or town centre, with a random jitter of ±15°.
  - Mix house variants (small house, terraced row, block of flats, church: at most one per town).
- **Forests.** Poisson-disc sampling at a spacing of `lerp(14, 5, density)`, mixing conifers and deciduous trees. In autumn, deciduous trees take autumn colours. In winter they are bare and have snow-capped conifers alongside.
- **Scatter.** Sparse trees across the whole map, at a spacing derived from `scatterTrees`.
- **Station props.** A platform slab (or two, for `side: "both"`), a canopy, a small station building and benches. Also place **people** along the platform as positions only; the scene animates them (§8).

### 5.8 Build entry point (`build.ts`)
```ts
function buildWorld(json: unknown): { world: World | null; report: Report }
```
`World` bundles the parsed layout, track geometry, graph, height profiles, structure spans, terrain grids, scenery placements and station geometry. `buildWorld` never throws for bad input; it returns a report instead.

## 6. Validation (`validate.ts`)

```ts
type Issue = {
  code: string;            // SCREAMING_SNAKE, stable
  severity: "error" | "warning";
  message: string;         // one sentence, includes numbers and a suggested fix
  path: string;            // JSON path, e.g. "tracks[1].points[2]"
  at?: [number, number];   // map location if applicable
};
type Report = { ok: boolean; issues: Issue[]; stats: Record<string, number> };
```

Required checks (codes are fixed):

| Code | Severity | Rule |
|---|---|---|
| `SCHEMA` | error | Zod failure; convert each Zod issue into a readable message |
| `DUPLICATE_ID` | error | ids unique across tracks, stations and services |
| `UNKNOWN_REF` | error | track, station or train references resolve |
| `TRACK_REF_CYCLE` | error | see §5.4 |
| `OUT_OF_BOUNDS` | error | all track samples within the terrain, with a 20 m margin |
| `FILLET_OVERLAP` | error | see §5.2 |
| `CORNER_TOO_SHARP` | error | see §5.2 |
| `JUNCTION_UNREACHABLE` | error | see §5.3 |
| `JUNCTION_POSITION` | error | `from.at` / `to.at` within `[0, length]` of the parent and not on a parent arc whose radius is < 150 m (turnouts on straights or gentle curves only) |
| `GRADE_EXCEEDED` | error | see §5.5 |
| `TRACK_CONFLICT` | error | two non-connected track samples closer than 4.5 m in plan with `|Δz| < 6 m`. Ignore pairs within 60 m of a shared junction. Report one issue per conflict cluster, not per sample |
| `STATION_RANGE` | error | platform `[at − length/2, at + length/2]` lies inside the track |
| `STATION_CURVE` | warning | platform overlaps an arc of radius < 300 m |
| `STATION_STRUCTURE` | warning | platform overlaps a bridge or tunnel span |
| `ROUTE_DISCONNECTED` | error | consecutive route tracks are not joined by a junction |
| `ROUTE_NOT_CLOSED` | error | `mode: "loop"` but the route does not return to its start |
| `STOP_NOT_ON_ROUTE` | error | stop's station track not in the route |
| `TRAIN_TOO_LONG` | warning | train length > platform length for any stop |
| `CAPACITY` | warning | trains on a route exceed (route length / (train length + 150 m)) |
| `DEADLOCK` | error | only from `simulate` (§7.4) |

Stats include total track length, number of junctions, bridge and tunnel lengths, number of trees and houses, and an estimated triangle count.

Write `test/validate.test.ts` with at least one failing fixture per error code, plus the two example layouts passing.

## 7. Simulation (`sim/`)

### 7.1 Clock
- Fixed timestep `dt = 1/30` s of simulated time, multiplied by `TIME_SCALE`.
- `Sim.step()` advances exactly one tick.
- The browser accumulates real time and calls `step()` as needed, at most 8 per frame.
- The sim never reads wall-clock time or `Math.random`. All randomness comes from `rng(seed)`.

### 7.2 Blocks (`blocks.ts`)
- Split each graph edge into blocks no longer than 200 m.
- Every junction node is a block boundary, and each switch's fouling zone (30 m either side of the node) is its own block.
- A block is either free or reserved by exactly one train.

### 7.3 Trains (`trains.ts`, `services.ts`)
Train state: `{id, serviceId, headEdge, headS, direction, speed, phase: "running"|"dwelling"|"waiting", dwellLeft, reserved: BlockId[]}`.

Per tick, for each train:
1. **Target.** The train's target is the nearest of:
   - the end of its reserved path;
   - its next stop's stopping point (the head stops so the train is centred on the platform);
   - the end of the route, for shuttles.
2. **Reserve.** Try to extend the reservation along the route until it covers `brakingDistance(speed) + 50 m`. Reserving across a switch sets that switch's state. Reservation is all-or-nothing per block. Release blocks once the train's tail has fully left them.
3. **Speed.** Compute the speed limit as `min(maxSpeed, sqrt(1.0 · radius))` over the next 100 m of arcs, giving a lateral acceleration of 1 m/s². Then accelerate, cruise or brake so the train can stop at the target. Use simple kinematics: `v² = 2·decel·d`.
4. **Advance** the head along the graph, following switch states.
5. **Dwell.** At a stop: set `phase = "dwelling"` for `dwell` seconds. Then emit a `departed` event.
6. **Shuttle ends.** At a shuttle end: dwell there, then flip direction. The old tail becomes the new head.

**Consist positions.** Car `k`'s front bogie is at arc-length `headS − (k·carLength + carLength·0.15)` behind the head, following the actual path back through the graph. To make this cheap and correct across switches, keep a ring buffer of the head's recent path (edge, s) sampled every 1 m. The rear bogie is `carLength·0.7` further back. The car body sits at the bogies' midpoint, with its heading taken from the vector between them and its z interpolated from the track heights.

**Spawning.** Trains of a service are spawned evenly spaced along its route at t = 0. The spawner must reserve their blocks; if it can't, it spaces them further apart.

### 7.4 Deadlock detection
If every train is either `waiting`, or has had `speed === 0` for more than 120 simulated seconds while not dwelling, emit `DEADLOCK`. The report must name the trains involved and the blocks they hold and want.

### 7.5 Sim API
```ts
class Sim {
  constructor(world: World, opts?: { seed?: number });
  step(): void;
  get time(): number;
  snapshot(): SimSnapshot;    // trains with per-car {x,y,z,heading}, switch states, block reservations
  events: SimEvent[];         // arrived/departed/deadlock, appended each tick; consumer may clear
}
```
`test/sim.test.ts` must check these invariants over 30 simulated minutes of `valley-loop`:
- no block is ever reserved by two trains;
- no two trains' consists ever come within 2 m of each other on the same edge;
- every service makes at least one stop per route traversal;
- there is no deadlock.

## 8. Scene (`scene/`)

### 8.1 Style
- `palette.ts` holds **all** colours: terrain bands by height and slope, water, ballast, rail, sleepers, platform, building walls and roofs (several), trees per season, sky by time of day, and fog colour.
- Use soft, slightly desaturated colours with warm light and cool shadows. The aim is a calm, illustrative look, not photorealism.
- Materials: `MeshLambertMaterial({ vertexColors: true, flatShading: true })` almost everywhere. Use one shared material where possible and put the colour into the vertex colours. No textures.
- **Terrain.** One mesh in a grid matching the heightmap, with per-face colour by height/slope band (grass, darker grass, rock, sand near water, snow in winter above some height). Add a low skirt around the edges so the map reads as a **diorama block standing on a table**:
  - darker earth-coloured sides;
  - a simple wooden table plane below;
  - a subtle base frame.
- **Water.** A flat plane at `seaLevel`, clipped to the terrain extent, slightly transparent, with gentle vertex-colour variation. No shader effects.

### 8.2 Track (`trackMesh.ts`)
- **Ballast.** A trapezoidal strip along each track's samples. Merge all ballast into one mesh.
- **Sleepers.** An `InstancedMesh` of boxes every 0.65 m. If the instance count gets too high, use every 1.3 m with slightly wider sleepers; it should read well from a distance.
- **Rails.** Two thin box-strips per track, merged.
- **Turnouts.** Nothing special in v0.1: overlapping track is acceptable.
- **Buffer stops.** A small red box at line ends that are not junctions.

### 8.3 Structures (`structures.ts`)
- **Bridges.** A deck along the bridge span, with piers every 25 m down to the ground (or water) and small parapet strips.
- **Tunnel portals.** A stone-coloured arch block at each `ground ↔ tunnel` transition, oriented to the track heading.
- **Stations.** A platform slab 1 m high and 4 m wide, a canopy over the middle 60% of its length, and a station building.
- **Town houses.** A small set of procedural meshes (box + gable roof, flat-roof block, terraced row, church with tower). Each is drawn as one `InstancedMesh` per variant, with per-instance colour through `instanceColor`.

### 8.4 Trains (`trainMesh.ts`)
- One `InstancedMesh` per car shape: a body box, a roof as a slightly narrower box, a dark window band, and a darker underframe. Build the mesh once and merge its parts.
- Per-instance colour comes from the service.
- Each frame, update instance matrices from `sim.snapshot()`. Reuse matrix and vector objects; allocate nothing per frame.

### 8.5 Life (Wimmelbild)
- **People on platforms.** An instanced capsule or two stacked boxes, randomly coloured. Most stand still. A few walk slowly back and forth along the platform. When a train dwells, about 30% of the people on that platform walk toward the train and disappear, and new ones appear. Keep the logic in the scene layer; it's purely cosmetic and seeded.
- **Smoke.** A puff at house chimneys: a few instanced low-poly spheres rising and shrinking, at about 10% of houses.

### 8.6 Lighting and camera
- **Lights.**
  - `HemisphereLight` (sky/ground) plus one `DirectionalLight` placed by `timeOfDay`.
  - Shadows use one `DirectionalLight` shadow map of 2048², fitted to the terrain bounds. The `S` key toggles it, and it defaults to on.
  - Add a fog colour from the palette.
- **Day/night.** If `dayLengthSeconds` is set, advance the time of day. Interpolate sky colour, light colour, intensity and direction. At night, give house windows a warm emissive colour via a second instanced window mesh whose material's emissive intensity is driven by the time.
- **Camera.**
  - A perspective camera with FOV 30, positioned to frame the whole diorama from roughly 35° elevation.
  - `OrbitControls` with damping and slow auto-rotate (0.15). Polar angle is clamped to 15°–75°; zoom is clamped.
  - **Follow mode** (`F` key) cycles the camera to follow trains. It sits behind and above the train, with smoothing.
- **Keys:**

  | Key | Action |
  |---|---|
  | `Space` | pause/resume the sim |
  | `1` `2` `3` | time scale 1×, 2×, 4× |
  | `F` | cycle follow train; `Esc` exits follow mode |
  | `S` | toggle shadows |
  | `H` | toggle HUD |
  | `R` | toggle auto-rotate |

### 8.7 HUD (`hud.ts`)
A small, unobtrusive HTML overlay in the bottom-left corner, hidden by default. It shows:
- layout name and simulated time;
- fps, draw calls and triangles (from `renderer.info`);
- the followed train's service and next stop.

Validation **errors** appear as a dismissible panel listing the issues.

### 8.8 Performance rules
- Static geometry is merged by material, giving at most about 120 draw calls total for `valley-loop`.
- Repeated objects are always drawn with `InstancedMesh`.
- No allocation in the frame loop.
- `renderer.setPixelRatio(Math.min(devicePixelRatio, 1.5))`.
- Rendering pauses when `document.hidden`.
- Target: fewer than 600k triangles for the example layouts.

### 8.9 Loading and hot reload
- `?layout=valley-loop` loads `layouts/valley-loop.json`; this is the default layout.
- `?seed=N` overrides the seed. `?t=SECONDS` pre-steps the sim headlessly to that time before the first render.
- During `vite dev`, editing a layout JSON rebuilds the world and scene without a full page reload. Use `import.meta.hot` with a JSON import, or a small Vite plugin. Keep the camera pose across rebuilds.

## 9. Public API (`src/api.ts`)

Exactly these exports form the stable surface, for use from Node and from the browser console (`window.dr`):

```ts
export { LayoutSchema, type Layout } from "./model/schema";
export function buildWorld(json: unknown): { world: World | null; report: Report };
```

## 10. CLI (`cli/`, run via `tsx`)

`package.json` scripts:

```json
{
  "dev": "vite",
  "build": "vite build",
  "test": "vitest run",
  "check": "tsx src/cli/check.ts",
  "simulate": "tsx src/cli/simulate.ts",
  "schema": "tsx src/cli/schema.ts",
  "screenshot": "tsx src/cli/screenshot.ts"
}
```

- `npm run check -- layouts/x.json [--json]`
  - Prints issues in a human-readable form, or the raw `Report` JSON with `--json`.
  - Exits with code 1 if there are errors.
- `npm run simulate -- layouts/x.json [--minutes 30] [--json]`
  - Runs the validation and then the simulation.
  - Prints the per-service stats and any deadlock.
  - Exits with code 1 on errors or deadlock.
- `npm run schema` writes `docs/schema.json`.
- `npm run screenshot -- layouts/x.json [--out shot.png] [--t 120] [--view overview|top|follow] [--size 1600x1000]`
  1. Start Vite in preview mode on a free port, or reuse a running dev server via `--url`.
  2. Open `?layout=…&t=…&view=…&shot=1` in headless Chromium, with WebGL via SwiftShader.
  3. Wait for `window.__drReady === true`, which `main.ts` sets after the first fully rendered frame in shot mode.
  4. Save a PNG.
  - In shot mode: auto-rotate is off, the HUD is hidden, and `view=top` uses a straight-down camera, which is useful for an LLM checking geometry.

## 11. `docs/LAYOUT_GUIDE.md`

Write this file for an LLM that will author layouts. It should cover:
- a short explanation of the coordinate system, `s`, and the fact that geometry is *derived* from waypoints;
- the schema summary (point to `schema.json`);
- the rules of thumb that avoid common errors:
  - keep waypoints at least `2·minRadius` apart at turns;
  - put junctions on straights;
  - keep parallel tracks at least 5 m apart;
  - give stations straight track of at least the train length;
  - a 30 m climb needs about 860 m of track at 3.5%;
- every validation code with a one-line fix hint;
- the recommended authoring loop: write → `check --json` → fix → `simulate` → `screenshot --view top` and `--view overview` → critique the composition;
- both example layouts, annotated.

## 13. Milestones and acceptance criteria

Implement in this order. Each milestone must leave the app runnable and the tests green.

1. **Skeleton.** Vite + TS + three.js scene with the diorama base, terrain from `features` and noise, OrbitControls, and a working palette. `npm run dev` shows terrain.
2. **Track geometry.** Schema, fillets, junctions, graph, heights and corridor shaping. Track, bridges and portals are rendered. `check` works with all geometric error codes. `geometry.test.ts` passes:
   - tangent continuity within 1e-6 rad at every segment join;
   - arc-length sum equals the sampled length within 0.1 m.
3. **Trains.** Blocks, services, consist positions, and the instanced train meshes. `simulate` runs, and the `sim.test.ts` invariants pass for `valley-loop`.
4. **Scenery and life.** Towns, forests, scatter trees, station props, people, smoke, seasons and day/night. `harbour-town` works.
5. **Tooling polish.** `screenshot` CLI, `query().describe()`, schema export, `LAYOUT_GUIDE.md`, hot reload, HUD, and a README with a quick start and controls.

**Definition of done for v0.1:**
- `npm test`, `npm run check` and `npm run simulate -- --minutes 30` pass for both example layouts.
- Both example layouts render at 60 fps on integrated graphics at 1080p, with fewer than 150 draw calls.
- `npm run screenshot` produces correct PNGs headlessly.

## 14. Code style

- TypeScript strict mode, ES modules, and named exports.
- Prefer small pure functions and plain data objects. Use classes only for `Sim` and, if helpful, scene builders.
- Keep files under about 400 lines. Each file begins with a 2–4 line comment saying what it does and how it fits the pipeline.
- Comment the *why* of the non-obvious maths (fillets, tangent construction, grade clamping, bogie placement) with a small ASCII sketch where it helps.
- Use magic numbers only in clearly named `const`s at the top of the file, or in `palette.ts` / `catalog.ts`.
- No `any`. Avoid premature abstraction: if something is used once, inline it.
- The README must explain how to add a new train type, a new building variant and a new validation rule, each in under 10 lines.
